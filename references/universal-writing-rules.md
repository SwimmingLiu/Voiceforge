# 通用写作规则

每次起草、改写、润色或编辑面向读者的内容时，都要执行本文件。它是 Voiceforge 的完整通用层，在可选个性化之前和之后各执行一次。事实和用户明确要求是硬约束，具体表达根据语境决定。

## 任务范围

以下操作都属于内容编辑，即使用户没有使用“写作”“改写”或“润色”等词：

- 新增、删除、替换或移动指定内容；
- 根据问题、反馈、审阅意见或新要求修改文档；
- 修改标题、段落、列表、表格、引用、链接、示例、目录、脚注或说明；
- 压缩、扩写、纠错、去重、统一术语或修复上下文和结构；
- 只改局部，同时保留不受影响的内容。

编辑前确认对象、范围、目标结果和受保护内容。明确修改要求高于一般风格偏好。未受影响的事实、含义和有效格式必须保留。纯代码逻辑、配置值、文件名和没有读者文案的机器数据不适用本规则。

## 优先级

要求冲突时，按以下顺序处理：

1. 保证事实准确，不编造信息、经历、感受或例子。
2. 保留原意，并执行用户最新的明确要求。
3. 保持事实关系和语法完整。
4. 使用朴素、易读、朗读自然的表达。
5. 最后调整节奏、标题和版式。

完整是指事实、原因、影响和动作之间的关系没有断裂，不是要求写得更长或重复解释。

## 事实和叙述身份

- 区分已确认事实、可编辑原文和未确认信息，不得把未确认内容写成事实。
- 第一人称只能用于有任务证据支持的行为、经历和判断。
- 中文内容描述作者自己的项目、行动或判断时，只有证据支持才能使用“我”。
- 一般中文讨论优先使用“我们”；直接面向一组读者时可用“大家”。同一段内不要反复切换称呼。
- 直接给读者操作说明，或原文已经直接称呼读者时，可以使用“你”。
- 集体称呼不能授权编造共同经历、共同感受、共识或群体意见。
- 除非用户明确删除或替换，保留名称、日期、数字、引用、链接、代码、产品名和来源。
- 引用来源中的百分比、倍数或其他衍生数字时，保留来源给出的数值并说明口径，例如“按报告的测算”。自行换算结果与来源不一致时，不得静默替换来源数值；应保留来源原值并指出差异，只有任务明确要求重新计算时才另行给出计算过程。
- 公开成稿需要点名第三方产品、组织或个人的负面结果时，即使材料来源可靠，也要先确认用户是否同意点名。没有明确确认时，使用中性、可核验的表述，不扩展成针对该对象的批评。
- 面向不熟悉主题的读者介绍产品、项目、功能、Skill、命令或其他专有名词时，在第一次出现处用一句自然的话说明它是什么、与当前内容有什么关系。原材料已经提供官网、仓库、安装页或原始资料链接时，把链接放在首次介绍附近；没有可靠来源时不要猜测链接。
- 用户只要求润色时，不得静默改变立场、结论、信息顺序或详略程度。

## 用词和句子

- 直接写明主体、对象、事实、过程和判断，保留必要的技术概念、产品名、代码、业务逻辑和设计决定。
- 每句话都应提供事实、限定、判断或关系。删除填充语、重复含义和空洞语气词。
- 语境已经明确动作时，用实际动作替代模糊动词和比喻。检查 `搞、弄、写、看、查、改、做、用、点、跑` 等单字动作词是否准确；含义模糊且可以自然替换时，改用整理、处理、编写、查看、检查、修改、完成、使用、点击、运行或其他符合实际动作的词。
- 不要机械替换正常动词或固定表达，避免改得更生硬或改变原意。
- 主语和指代要清楚，动作要有对象，修饰关系不能含混。上下文明确时可以自然省略主语。
- 表达连接、整合或合并关系时，动作主体不能同时出现在自己的对象集合中。例如 `A 把 X 和 Y 合并` 时，A 不能也是 X 或 Y。省略宾语时，读者应能从上下文自然补出宾语。
- 长短句交替，既不要连续使用碎片句，也不要把多个独立判断挤进一个过长句子。
- 表达应像人在自然解释问题，不依赖填充词或压缩到不合语法的伪口语。
- 需要口语节奏的内容应保留承担语法和节奏作用的虚词，例如 `在、的、了、的时候`。不要为了压缩而让朗读发紧；补足必要虚词和删除多余语气词是两种操作，应分别判断。

## 逻辑和结构

- 按信息的真实关系组织内容。材料包含原因、影响和应对时，不要删掉中间推理。
- 重要判断需要必要解释，但不要用不同说法重复同一结论。
- 相邻段落不要重复同一个数字、事实或结论。事实段负责交代信息，反应或判断段直接写反应和判断，不复述前段已经出现的数字；确有必要的收尾总结除外。
- 比较工具或方案时，使用具体能力、限制和适用场景。
- 连续推理使用段落；并列概念、步骤、检查项或参考信息使用列表。
- 同一列表中的项目保持相同逻辑层级，不要为了节奏把每句话拆成项目。
- 主题、过程或边界变化时再分节，不强求固定节数、对称标题或套用模板。
- 开头可以交代语境、事实或判断，不必总是先下结论。信息完整后直接结束，不追加价值升华。
- 区分整篇标题和文内小标题。文内小标题主要充当内容标签；整篇标题可以表达材料已经支持的动作、变化、结果或作者判断，让读者知道正文会讨论什么。
- 整篇标题中的第一人称、动作、时间、数量、结果和判断都必须有材料的直接证据。只有材料明确证明作者开发、制作、设计、新增或开源某个对象时，才能使用相应的所有权表达；涉及第三方产品时，只写已经证实的使用、测试、发现和判断。
- 标题不要加入口号、虚构行动、强行对比或装饰性排比，也不要为了制造观点、节奏或态度，在冒号、逗号或破折号后自行添加没有材料支持的行动建议、转折判断、对仗句或口号。
- 每个标题下应有足够内容，不为单个孤立句子单独建节。

## 常见 AI 写作模式

以下表达是复核信号，不是机械禁用词。只有它承担真实事实、原因、对比或限定时才保留：

- 删除没有必要信息的时代背景、泛化铺垫和“值得注意”等固定过渡。
- 把无依据的重要性、里程碑和价值判断改成已确认的动作、变化或结果。
- `专家表示`、`研究显示`、`很多用户反馈` 等模糊归因必须给出具体来源；没有来源就删除权威声称。
- 删除没有证据支持的因果分析、意义拔高和“更深层次”结尾。
- 把模板化的 `虽然有挑战但未来可期` 改成已确认的限制、结果或下一步。
- 删除成稿中的聊天残留和恭维，包括问候、夸奖问题和泛泛的继续帮助邀请。
- 合并重复的不确定词，同时保留真实的不确定程度。
- 检查强行三段式、虚假的“从 A 到 B”、无必要的同义词轮换、过多破折号、装饰性加粗和 emoji。

## 应避免的表达

- 不得编造朋友、用户、反馈、个人经历、使用案例或情绪。
- 不要用口号、宣传术语、新奇比喻、拟人或装饰性意象包装普通事实。
- `核心问题是`、`关键区别是`、`原因很简单`、`综上所述` 等模板句没有新增信息时应删除。
- 不要反复使用否定式排比制造对比；只有确实需要纠正常见误解时才使用。
- 不要把引号当装饰，也不要添加无必要的括号翻译。
- 不要用模糊的运营或管理隐喻隐藏动作，应写明主体、动作和对象。
- 结尾不要加入没有材料支持的鼓舞、教训或更大意义。
- 除非任务本身要求，不要在成稿中写生成时间、模型名、API 细节、脚本路径或维护过程。

## 不同内容类型

- **长文章、博客、演讲和传记：**第一人称必须有证据支持。说明必要的原因和过程；主题确实变化时使用朴素的二级标题。
- **网站、产品说明和落地页：**直接说明产品是什么、能做什么、适合谁和有哪些限制，不替读者断言产品优秀。
- **短社交内容：**可以使用自然口语节奏，但不得虚构前提、受众反应或共同经历。
- **文档、API 说明和正式通知：**优先保证准确清楚，直接说明操作、条件和必要解释。

## 结构和格式

- 文档已有独立 H1 时，不要在正文第一行重复标题。
- 修改现有内容时，保留要求范围之外的 Markdown 层级、链接、代码和必要格式。
- 直接返回修改后的成稿；只有用户要求时才附修改说明。
- 除非用户要求翻译，保留原文语言。使用对应语言的标点和空格规范，代码标点不变。
- 中文与相邻的拉丁字母或数字之间留一个半角空格，中文句末使用全角标点。纯英文和代码使用半角标点。

## Markdown 删除语义

用户要求省略、删除、移除、取消或不再出现某项内容时，要从目标文档中彻底删除。不要把原内容改写成“不得包含某项”“某项已取消”或“某项不受支持”。

删除范围包括标题、正文、列表、表格、引用、注释、代码块、示例、链接、目录、脚注和相关解释。删除后修复上下文和结构，避免残留引用、断句或空标题。

除非用户明确要求写成禁止规则、弃用通知或历史记录，目标文档中不得保留被删除内容的任何形式。完成后检查全文和差异，确认原内容和否定式改写都没有残留。

“不要修改某项”和“不要删除某项”表示保护内容，不适用本删除规则。

## 英文写作

- 使用常见、直接的词和自然缩写。
- 优先使用 `if`、`so`、`and`、`but` 等简单连接词，只有语境需要时才用正式连接词。
- `That said`、`It is worth noting that`、`In conclusion` 和 `At the end of the day` 等固定过渡没有新增信息时应删除。
- 不要为英文概念添加无必要翻译。

## 完成检查

文件型内容运行：

```bash
python3 <skill-dir>/scripts/tone_lint.py <文件>
```

聊天中的短文本从标准输入传入，不要只为检查而创建临时文件：

```bash
python3 <skill-dir>/scripts/tone_lint.py -
```

修复所有 `FAIL` 后重新运行。每个 `WARN` 都要结合实际语境判断；只有确实承担信息作用时才保留。检查通过后，通读并朗读完整成稿，重新核对本文件、事实、隐私、引用、受众和用户明确要求。人工检查还要覆盖脚本无法判断的内容：必要虚词是否缺失；相邻段落是否重复数字、事实或结论；长句的主语、指代和动作对象是否清楚；动作主体是否进入自己的对象集合；数字、百分比和倍数是否与来源及其口径一致；公开点名第三方负面结果是否已经获得确认；专有名词首次出现时是否为陌生读者提供了必要说明。脚本只能识别已知模式，不能代替人工判断。
